# Migration — MySQL ticket → PostgreSQL (v1.3)

## Kebijakan v1.3 (berlaku atas seluruh dokumen)
Pemilik mengizinkan agent lokal mengakses MySQL dan PostgreSQL, read dan write. Akses aktual bergantung pada credential, jaringan, privilege dan sandbox agent; jangan mengakali kontrol. Gunakan Database-Access.md sebagai kebijakan otoritatif. Read produksi yang ringan dan write rutin terukur dalam target yang telah didaftarkan tidak memerlukan konfirmasi per query. Operasi produksi berisiko tinggi, perubahan schema produksi, bulk correction, freeze/cutover dan tindakan irreversible memerlukan persetujuan runbook khusus. Source legacy tetap read-only; database bukan source code. Discovery tidak mengubah data bisnis produksi. Semua rancangan teknis termasuk DDL, jumlah tabel/index dan alias adalah kandidat, bukan kontrak tetap. Direct matching Workzone diutamakan; buktikan keunikan global setelah normalisasi, jika ambigu gunakan pembeda yang terverifikasi, jangan menebak. Alias hanya bila terbukti diperlukan. Requirement bisnis, integritas historis, keamanan dan stack tetap wajib. Lihat Discovery-Protocol.md dan Decision-Log.md.


## 1. Policy and boundaries
One-time historical migration is mandatory. Keep existing DOMPIS serving until approved cutover. Read `ticket` from a verified snapshot/restore; do not import `ticket_raw` or piloting as runtime facts. New canonical `tickets` contains eligible historical and live incidents, including pre-2026. Keep encrypted full source backup and restricted cold archive. NOSSA and NOSSA Closed alone update ongoing upstream facts; MySQL connection removed from runtime after migration. No direct MySQL dump import to incompatible PostgreSQL schema; ETL using Bun TypeScript and validated driver, PostgreSQL batch writes through Drizzle/parameterized SQL or COPY into disposable staging for measured need. All production actions require authorization.

## 2. Preflight and discovery
- Capture exact `SHOW CREATE TABLE ticket`, MySQL version, timezone/sql_mode, generated columns, collations, index/FK metadata and migration versions. Use read-only session; compare against Legacy-Field-Mapping.md and approve drift. Profile row count, distinct exact and normalized incident (binary comparison vs MySQL collation), ID min/max, null/invalid values, date ranges, manual records, status, workzone, classifications and eligible KPI. Do not log actual customer fields.
- Backup current DB and test restore separately; confirm source storage integrity. Earlier corruption in raw data is not proof ticket table is clean; verify extract/restore. If corrupt/unreadable rows, stop and record scope of failure; never use force-recovery as normal production process. Source backup remains intact.
- Use fixed snapshot ID, source identity, schema hash, extraction timestamp, counts, file/segment checksums and high-water ID in manifest. Immutable snapshot permits resumable keyset export; `MAX(id)` alone does not track changes to existing rows. Confirm source timezone: MySQL TIMESTAMP session UTC, legacy VARCHAR dates parse according to approved field/timezone rules. Profile collisions after normalization. Confirm retention, PII allowlist and manual ticket eligibility.
- Resolve dimension mappings from approved masters before import. Unknown workzone must deny ordinary access; review only with authorized global scope and explicit remediation permission. Migrate allowed users separately by username; verify password hashes or reset, do not copy sessions/technician access.

## 3. Offline ETL (isolated staging first)
1. Generate Drizzle schema from v1.3 DDL; apply only to disposable PG first. Seed dimensions. Ensure backup space and role permissions. Run importer in dry-run mode by default; report mapping counts/issues, no DB writes in dry-run. Never query production DB from unapproved agent.
2. Use a restored snapshot (preferred) or approved consistent snapshot export, not many unrelated live queries. Read `WHERE id_ticket > :last AND id_ticket <= :max ORDER BY id_ticket LIMIT :batch` with explicit scalar projection. Start 300–500 rows, bound bytes and memory; tune for HDD/SSD. Avoid long read transactions on busy MySQL; read replica/restore preferred. Export encrypted segments when needed; manifest verifies every segment. No unbounded array or OFFSET on source.
3. Normalize using dedicated legacy adapter; preserve originals in approved cold archive, use typed target fields per mapping. Unknown columns block import until mapped. Nulls/missing semantics explicit, no artificial SLA or timestamps. Normalize incident collision groups across entire snapshot before canonical import; never pick winner by largest ID alone. Approve deterministic winner based on trustworthy evidence, preserve each source ID and original eligible values; quarantine unresolved/invalid or explicitly excluded rows with reason. Retain full backup irrespective of online retention.
4. Acquire same writer advisory lock as sync; pause worker. Each chunk transaction: check run/manifest identity, lock by incident sorted, insert new canonical UUID or reuse existing UUID; create/update archive mapping; write checkpoint and counters atomically. On replay same immutable snapshot + legacy ID + row hash -> no-op; if changed hash in same snapshot -> manifest error, stop. If next approved snapshot/delta, compare source provenance and evidence, never overwrite accepted newer NOSSA facts. `ticket_legacy_archive` holds latest approved legacy row for each old ID; previous snapshot evidence retained in encrypted manifests/backups. Archive unresolved rows with NULL ticket_id and reason; reconcile explicitly later. `sync_runs` stream legacy_migration; checkpoint stream `legacy_migration:<snapshot-id>`, state includes last committed ID and manifest. Do not advance upstream coverage. Do not generate historical status events from snapshot. Bounded retries for transient DB errors only; rollback failed chunks. Resume from last committed ID on same manifest. Re-run full import after completion must not change UUID/version or duplicate archive.
5. If staged import already overlaps live records, do not replace newer source facts with old snapshot; archive maps existing UUID and fill only approved missing historical fields after review. `data_origin` immutable; source hash/endpoint never invented for legacy. Handle new snapshot delta with explicitly approved mode; no deletion on source absence. For large dataset compare direct batch insert vs isolated staging COPY, never sacrifice validation/constraints.

## 4. Reconcile and shadow
- Compare baseline before live sync (same snapshot) by exact row accounting and metrics in Migration-Validation.md. Preserve legacy classifier output for comparison; new rules require documented signed delta. No production traffic until mandatory reporting fields have resolved disposition. Record source/target manifests and validation outcomes.
- Enable one bounded worker with approved API budget. Scan full accessible active history and recent closed overlap; don't re-fetch pre-2026 bulk (API floor). Backfill only known gaps/needed windows from 2026; older history stays migrated. Status_Date filter, page cap, drift handling per Sync-Engine.md. Coordinate old and new workers sharing key; avoid competing scans. Source conflicts quarantine. No absence-based close. Compare scope, status, closed date, TTR, bucket, monthly totals and UI drilldown. Distinguish migrated vs verified data.

## 5. Final delta and cutover
- Preferred: rehearse full import from snapshot, then final short controlled write freeze or approved CDC/delta strategy. `id_ticket` detects inserts only; `synced_at` may not track manual edits or deletions, so do not trust it without validation. If reliable change tracking unavailable, take final consistent snapshot and compare row hashes / re-import changed eligible rows (capacity planning required), or keep freeze for final export. Detect deletions explicitly and obtain retention decision; do not auto-delete PG. Pause/coordinate live writers during final legacy delta; merge older legacy vs newer accepted upstream according to provenance, then run bounded final source reconcile.
- Repeat validation at fixed snapshot/revision/asOf; reconcile new upstream changes separately. Sign off on counts, unresolved exceptions, performance/security, backup/restore and rollback. Switch reverse proxy routes; require fresh login. Monitor data freshness, DB disk/locks/pool, 429, errors and parity; keep old DB/application accessible for authorized rollback and backups. No old runtime DB dependency in new services. Revoke temporary migration credentials after acceptance.

## 6. Rollback
If security leak, unexplained count gap, severe stale data or SLO failure: stop new traffic and worker, revert proxy to legacy after verifying old system is safe, coordinate upstream budget, preserve PG and archive for analysis. Do not overwrite legacy with new data automatically. Track any new local writes (MVP ticket read-only); reconcile before return if needed. Restore verified backups only for data loss/corruption. Do not decommission legacy until owner accepts retention and rollback window. Record exact commands, metrics and decisions in Handover.md.

## v1.3 master/user migration (before ticket ETL)
Use Master-Data-Migration.md as the authoritative ordering and field mapping. MySQL `area` maps to PostgreSQL `service_area`; MySQL `service_area` maps to PostgreSQL `workzone`. Build new top-level `area` from owner-approved region membership; never infer from QOSMIC Area 3 naming. Migrate approved region/branch parent paths, then SA/workzone, aliases, users and effective scope grants before ticket import. Preserve old IDs in encrypted typed manifest by source table (not unqualified old integer IDs). Read both direct users.region_id/branch_id/area_id and junction grants; compare actual legacy effective access on restored snapshot, do not union blindly. Approve each changed scope or withhold account pending review. Null parent or duplicate code under same parent must be adjudicated before activation. Unknown ticket scope may be retained NULL with quality flag and isolated review; no silent drop. Migration account never enabled by default; hash compatibility review and reset where required, no legacy sessions/tokens. Compare authorized workzone sets and counts before cutover, test grant revocation, reject widening without explicit sign-off. Keep legacy full backup, source checksums, masters and grant manifest under restricted retention. Freeze master edits during snapshot or include final delta with same ID mapping; no delete by absence.
