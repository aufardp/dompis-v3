## ADR-007 details — 2026-11-26

- Context: scaffold had only `regions → branches → workzones`, direct `user_workzones`, and hardcoded role strings; required model is five levels, multiple scopes and role/action separation. The registered local project database contained no business rows before migration.
- Evidence: schema migration generated by Drizzle and applied with the Bun SQL Drizzle migrator; local PostgreSQL 18.7 reports 19 public tables, 21 FKs, a `NULLS NOT DISTINCT` scope unique index, and the exactly-one-target check. Synthetic insert/rejection checks passed inside a rolled-back transaction.
- Decision: represent `area → region → branch → service_area → workzone`; scope grant targets exactly one typed FK; use a role-permission catalog rather than legacy role enum. Leave roles, permissions, master data, users and grants unseeded until policy/crosswalk decisions are approved. No Workzone aliases are introduced without evidence.
- Consequences: current scope handles overlap at the data model and prevents duplicate identical grants; application resolver and deny-by-default API enforcement are still required. Total table count is now 19, not 17, because of separate new hierarchy and RBAC entities. Existing scaffold-only columns/tables are removed by migration `0001`; the migration is unsafe for a database containing data and must not be promoted as-is.
- Rollback: no down migration is generated. On the empty local database, a reset requires verified target identity and a reviewed reverse/recreate procedure. For any nonempty database, create a reviewed additive data-preserving migration and backup first.
- Validation: `bun run typecheck`, `bun run build`, `bun run db:generate`, `bun run db:migrate` (including repeat run), PG catalog checks, and synthetic transactional scope-constraint assertions passed. No owner approval of role mapping, crosswalk, or production rollout is implied.

## ADR-008 details — 2026-11-26

- Context: schema and shared authorization lookup existed, but API had only health routes. Security.md requires opaque hashed sessions, Argon2id, strict Origin and CSRF checks, generic login failures, throttling, and active identity revalidation.
- Evidence: Elysia 1.4.32 and Bun 1.4.5 are pinned in the project; Context7 docs were checked for Elysia cookie/app.handle behavior and Bun 1.4.2 password APIs. Synthetic integration tests against local PostgreSQL exercised CSRF/Origin rejection, Argon2id login, cookie flags, session read/revocation, generic invalid credentials, and throttling.
- Decision: add `/auth/csrf`, `/auth/login`, `/auth/logout`, `/auth/me`; store only SHA-256 of random 32-byte session tokens; keep credential/session SQL in the DB package. CSRF uses a random cookie/header double-submit pair with constant-time comparison and exact configured Origin validation. Use bounded process-memory account/IP counters with a conservative 10 failures per 15 minutes while deployment remains one API process; do not trust forwarded IP headers.
- Consequences: no new dependency or schema object. Login requires a configured `APP_ORIGIN`. Permission resolution is current per `/auth/me`, but protected product routes and administrative mutations still need shared guards. The limiter resets on restart and cannot coordinate replicas; scaling out is blocked until a durable shared approach is reviewed.
- Rollback: revert `apps/api/src/auth.ts`, `apps/api/src/app.ts`, `apps/api/src/index.ts`, `packages/db/src/authentication.ts`, exports and tests, plus this ADR and Phase 2/Handover notes. No migration or persistent business data change; tests roll back their transaction.
- Validation: `bun run typecheck`, `bun run build`, `git diff --check`, and `bun --env-file=.env test apps/api/src/auth.test.ts` passed; the auth test reported 1 pass and 28 expectations. `packages/db/src/authorization.test.ts` also passed (1 test, 9 expectations). Database user/role/session counts remained 0 after rollback. Production deployment and horizontal scaling are not approved by this decision.
- Follow-up: `createPermissionGuard` adds Elysia's `requirePermission` macro; a protected route receives the fresh authorization context only after session+permission checks. It sets `Cache-Control: private, no-store`. Integration coverage includes missing-session 401, authorized 200, missing-permission 403, and no-store. This remains a reusable extension; no business route exists or is protected yet.

Append ID/date/status/context/evidence/alternatives/decision/consequences/test/rollback/owner approval if required. Supersede rather than erase decisions. Update schema, docs and Handover in same change.

## ADR-009 — Configurable local API proxy (2026-11-26)

- Status: implemented locally; development-only.
- Context: local login uses same-origin Vite proxies for `/auth`, `/tickets`, and `/health`. API port 3000 was occupied by an unrelated/unidentifiable listener during local verification.
- Evidence: API and web started on loopback ports 39871 and 5173; proxied `GET /auth/csrf` returned 200 and proxied `GET /auth/me` returned the expected 401 for anonymous access. No login credentials or DB writes were used.
- Alternatives: stop the listener on 3000 (not safe because its owner was not identified); keep a fixed proxy and leave local login unavailable while the port is occupied.
- Decision: derive Vite proxy target from `process.env.API_PORT`, with 3000 as the default; both local processes receive the same override.
- Consequences: local development can avoid the port conflict without changing browser origin, CSRF validation, cookies, or production deployment. No dependency or runtime API changes.
- Validation: `bun run typecheck:web`, `bun run build:web`, desktop Chrome render, proxied CSRF/session smoke checks, and `git diff --check` passed. Interactive login/logout with a provisioned synthetic user remains unverified.
- Rollback: restore the fixed `http://127.0.0.1:3000` proxy target and remove the local setup note. No database rollback.
