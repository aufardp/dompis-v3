## ADR-007 details — 2026-11-26

- Context: scaffold had only `regions → branches → workzones`, direct `user_workzones`, and hardcoded role strings; required model is five levels, multiple scopes and role/action separation. The registered local project database contained no business rows before migration.
- Evidence: schema migration generated by Drizzle and applied with the Bun SQL Drizzle migrator; local PostgreSQL 18.7 reports 19 public tables, 21 FKs, a `NULLS NOT DISTINCT` scope unique index, and the exactly-one-target check. Synthetic insert/rejection checks passed inside a rolled-back transaction.
- Decision: represent `area → region → branch → service_area → workzone`; scope grant targets exactly one typed FK; use a role-permission catalog rather than legacy role enum. Leave roles, permissions, master data, users and grants unseeded until policy/crosswalk decisions are approved. No Workzone aliases are introduced without evidence.
- Consequences: current scope handles overlap at the data model and prevents duplicate identical grants; application resolver and deny-by-default API enforcement are still required. Total table count is now 19, not 17, because of separate new hierarchy and RBAC entities. Existing scaffold-only columns/tables are removed by migration `0001`; the migration is unsafe for a database containing data and must not be promoted as-is.
- Rollback: no down migration is generated. On the empty local database, a reset requires verified target identity and a reviewed reverse/recreate procedure. For any nonempty database, create a reviewed additive data-preserving migration and backup first.
- Validation: `bun run typecheck`, `bun run build`, `bun run db:generate`, `bun run db:migrate` (including repeat run), PG catalog checks, and synthetic transactional scope-constraint assertions passed. No owner approval of role mapping, crosswalk, or production rollout is implied.

## ADR-008 details — 2026-11-26

- Context: schema and shared authorization lookup existed, but API had only health routes. Security.md requires opaque hashed sessions, Argon2id, strict Origin and CSRF checks, generic login failures, throttling, and active identity revalidation.

Synthetic integration tests against local PostgreSQL exercised CSRF/Origin rejection, Argon2id login, cookie flags, session read/revocation, generic invalid credentials, and throttling.
- Decision: add `/auth/csrf`, `/auth/login`, `/auth/logout`, `/auth/me`; store only SHA-256 of random 32-byte session tokens; keep credential/session SQL in the DB package. CSRF uses a random cookie/header double-submit pair with constant-time comparison and exact configured Origin validation. Use bounded process-memory account/IP counters with a conservative 10 failures per 15 minutes while deployment remains one API process; do not trust forwarded IP headers.
- Consequences: no new dependency or schema object. Login requires a configured `APP_ORIGIN`. Permission resolution is current per `/auth/me`, but protected product routes and administrative mutations still need shared guards. The limiter resets on restart and cannot coordinate replicas; scaling out is blocked until a durable shared approach is reviewed.

Database user/role/session counts remained 0 after rollback. Production deployment and horizontal scaling are not approved by this decision.

- Status: implemented locally; development-only.
- Context: local login uses same-origin Vite proxies for `/auth`, `/tickets`, and `/health`. API port 3000 was occupied by an unrelated/unidentifiable listener during local verification.

## ADR-010 — Baseline API response security headers (2026-11-26)

- Status: implemented locally.
- Context: Security.md requires `nosniff` and a restrictive referrer policy; the JSON API had no shared hook applying headers to every route, including health and not-found responses.
- Evidence: Elysia 1.4.32 is installed. Its local type declarations and lifecycle reference confirm `onRequest` runs before routing and exposes `set`; API typecheck passed after adding the hook.
- Alternatives: duplicate headers in each route (easy to miss) or configure at deployment proxy only (not all local execution paths use that proxy).
- Decision: set `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer` in a global `onRequest` hook before route registration.
- Consequences: all API responses receive these baseline headers without changing payloads, auth decisions, cookies, or schemas. CSP and HSTS remain deployment-layer controls; do not enable HSTS until TLS is validated.
- Validation: `bun run typecheck:api` and `git diff --check` passed. No HTTP response assertion was run in this slice.
- Follow-up validation: local API on `127.0.0.1:39871` returned the three headers on both `GET /health/live` (200) and an unknown route (404); process stopped after the check.
- Rollback: remove the global hook and this ADR entry; no DB or persistent state changes.

## ADR-011 — Generic API error responses (2026-11-26)

- Status: implemented locally.
- Context: Security.md requires generic errors with request IDs and prohibits query/stack disclosure. Elysia's default development error response can include implementation detail, and validation/not-found errors did not have a consistent correlation ID.
- Evidence: Context7 documentation for Elysia `onError` says returning a value replaces the default response and context supplies error code, error and status. Current API route errors are returned as typed values; thrown/validation/framework errors flow through the app hook.
- Alternatives: rely on production-mode Elysia redaction (does not provide a consistent request ID and is environment-dependent); add handlers per route (easy to miss).
- Decision: global error hook preserves valid 4xx/5xx status, returns only `not_found`, `invalid_request`, or `internal_error` plus a random UUID request ID, and sets `X-Request-ID`. It logs only 5xx event, request ID, framework error code and error type; it never logs message/stack/body/query.
- Consequences: thrown errors, parsing/validation failures and unknown routes no longer reveal framework details through their response. Explicit business errors returned by route handlers keep their existing documented shape.
- Validation: `bun run typecheck:api` and `bun run build:api` passed. Local API smoke checks on `127.0.0.1:39871` verified unknown route HTTP 404 returns only `not_found` and request ID, while invalid login body HTTP 422 returns only `invalid_request` and request ID. The process was stopped after the checks. No synthetic thrown-500 request was run.
- Rollback: remove the global error hook and this ADR entry; no database change.

## ADR-012 — Request correlation on every API response (2026-11-26)

- Status: implemented locally.
- Context: request ID existed only on errors handled by `onError`; handled readiness failures and successful requests lacked a response ID to correlate with operational records.
- Evidence: global Elysia `onRequest` runs before route handlers and can assign response headers. The API's readiness failure handler logs a sanitized event and can reuse the same header value.
- Alternatives: generate separate IDs in each endpoint (inconsistent); rely on proxy-generated IDs (not guaranteed in local execution).
- Decision: generate a UUID in the global request hook, add `X-Request-ID` to every API response, reuse it in generic error body and sanitized readiness-failure log.
- Consequences: API consumers can reference a stable per-request ID on successful and handled-error responses; no response payload, auth, business query, or DB schema change.
- Validation: `bun run typecheck:api`, `bun run build:api`, and loopback checks of a success route, 404, and invalid request confirmed an ID header on each; error body IDs match the header. No database request was made.
- Rollback: remove request ID generation/reuse from app hooks and this ADR entry; no persistent state changes.

## ADR-013 — Accurate login throttle retry interval (2026-11-26)

- Status: implemented locally; production deployment remains subject to ADR-008's single-process limitation.
- Context: the login limiter blocked a request when an account or IP bucket reached its threshold, but always returned `Retry-After: 900`, even when the affected bucket would reset sooner.
- Evidence: static review of `LoginLimiter` showed each bucket already records its reset timestamp; the response discarded that timestamp and used the full configured window.
- Decision: calculate the maximum remaining reset interval among blocked account/IP buckets. If the bounded in-memory bucket map is full and a new key cannot be admitted, also account for the earliest bucket expiration that frees capacity. Return a minimum of one second and expose no bucket keys or counters.
- Consequences: rate limit policy and thresholds remain unchanged; clients receive a retry interval consistent with the limiter state. No dependency, database, schema, response body, or logging changes.
- Validation: `bun run typecheck:api`, `bun run build:api`, and `git diff --check` passed. No automated test or runtime DB interaction was performed in this change.
- Rollback: restore the fixed 900-second header calculation and boolean limiter check; no database or persistent state rollback is needed.

## ADR-014 — CSRF token encoding validation (2026-11-26)

- Status: implemented locally.
- Context: the double-submit CSRF check verified JavaScript string length before calling `timingSafeEqual`. Equal character counts can encode to buffers with different byte lengths; Node throws on a length mismatch instead of returning a comparison result.
- Evidence: the generated token is 32 random bytes encoded as unpadded base64url, exactly 43 ASCII characters from `[A-Za-z0-9_-]`; the previous guard accepted other same-character-length strings.
- Decision: require both cookie and header to match the generated token alphabet and exact 43-character form before constant-time comparison. Malformed encodings fail closed as CSRF rejection.
- Consequences: valid generated tokens retain identical behavior; malformed input no longer reaches a throwing comparison. No schema, dependency, response body, or business policy change.
- Validation: `bun run typecheck:api`, `bun run build:api`, and `git diff --check` passed. No runtime request or automated test was performed in this slice.
- Rollback: restore the previous length-only guard; no database or persistent state rollback is needed.

## ADR-015 — Preserve password verifier failures (2026-11-26)

- Status: implemented locally.
- Context: login caught every exception from `Bun.password.verify` and converted it to `passwordMatches=false`, making verifier/runtime or malformed stored-hash failures indistinguishable from a normal bad password.
- Evidence: the catch block swallowed all exceptions; the API already has a global error handler that maps unexpected exceptions to a generic 500 response with a request ID and logs only sanitized error type/code.
- Decision: allow verifier exceptions to propagate to the global handler. A normal `false` verification result remains a generic 401; unexpected verifier failure becomes sanitized 500.
- Consequences: no exception details or credential material are exposed; monitoring can distinguish infrastructure/hash failures from routine failed login attempts. No schema, dependency, or business policy change.
- Validation: `bun run typecheck:api`, `bun run build:api`, and `git diff --check` passed. No automated test or runtime request was performed in this slice.
- Rollback: restore the catch that converts verifier exceptions to `false`; no database or persistent state rollback is needed.

## ADR-016 — Explicit session cookie expiration attributes (2026-11-26)

- Status: implemented locally.

## ADR-019 — API request body limit (2026-11-26)

- Status: implemented locally; future routes with larger payloads require an explicit contract review.
- Context: Elysia's Bun server default allows request bodies up to 128 MiB. The current API accepts only small JSON auth bodies, so the default permits unnecessary memory and parsing work before field-level validation.
- Evidence: Context7 Elysia serve-option documentation and Bun server references identify `maxRequestBodySize` in bytes with a 128 MiB default. Current login schema limits username to 160 characters and password to 1,024 characters; no API upload or sync payload route exists.
- Decision: configure the API server maximum request body at 16 KiB. This leaves headroom for escaped UTF-8 JSON while bounding malformed oversized requests. Keep upstream ingestion in the separately bounded worker.
- Consequences: oversized API bodies are rejected by the server before route schema handling; no dependency, DB, route payload schema, or business behavior changes. Any future larger request must revisit this limit with its payload contract.
- Validation: `bun run typecheck`, `bun run build`, and `git diff --check` passed. No oversized runtime request or automated test was performed in this slice.
- Rollback: remove `MAX_REQUEST_BODY_BYTES` and the Elysia `serve.maxRequestBodySize` setting, and remove the Security.md requirement/ADR-019; no database rollback is needed.

## ADR-020 — Concurrent login attempt reservation (2026-11-26)

- Status: implemented locally; limiter remains bounded and process-local per ADR-008.
- Context: the login limiter previously incremented failures only after the asynchronous identity query and password verification. Parallel requests could all pass the threshold check before any failure was recorded.
- Evidence: source flow awaited identity lookup and Argon2id before calling `failed`; there was no in-flight count or reservation.
- Decision: reserve one account/IP attempt synchronously before DB/hash work. Block when failed attempts plus in-flight reservations reach 10. Finish each reservation as invalid credentials, successful account authentication, or release on unexpected error. Success clears account failures while retaining IP failures; unexpected errors release slots without counting as bad credentials.
- Consequences: concurrency cannot bypass the configured per-account/IP cap; Retry-After reports at least one second for requests blocked only by in-flight work. No DB schema, dependency, password policy, or threshold changes.
- Validation: `bun run typecheck:api`, `bun run build:api`, and `git diff --check` passed. No concurrency runtime request or automated test was performed in this slice.
- Rollback: restore the prior limiter check/failure update flow and remove the in-flight reservation/finalization; no database or persistent state rollback is needed.

- Context: HTTP login is implemented, but the development database has no user. Creating an admin endpoint before capability approval would invent administrative authority; leaving no safe first-account path also prevents local authentication QA.

- Decision: add `bun run auth:bootstrap`, restricted to loopback PG18 `dompis_v3`, a first run with no users/permissions/role grants/prior bootstrap event, and an explicit one-of-six role selection. Password is entered in hidden terminal mode and stored only as Argon2id hash. User creation and a PII-minimal audit event commit in one transaction. The account gets no scope, global grant, or role permission.
- Consequences: an operator can provision a local account for login QA without implicitly granting product access. The command is not a general user-management interface and does not run during application startup. It refuses production configuration and repeat bootstrap.
- Validation: Bun 1.4 docs lookup confirmed parameterized SQL and `SQL.begin` transaction/rollback behavior; strict TypeScript check, Bun bundle, root typecheck/build, and `git diff --check` passed (see Handover). The CLI was not executed, and no account/password was created.
- Rollback: remove `auth:bootstrap` from package scripts and delete `scripts/bootstrap-first-user.ts`; no database rollback because command has not been run. If it is run later, remove the user/audit record only through a reviewed local rollback after checking sessions/references.

## ADR-029 — Bootstrap uses application database credentials (2026-11-26)

- Status: implemented locally.
- Context: the first-user bootstrap initially preferred `MIGRATION_DATABASE_URL`, which may have broader schema privileges than the application database role.

## ADR-030 — Clear rejected session cookies (2026-11-26)

- Status: implemented locally.
- Context: `/auth/me` rejected malformed or stale session tokens but left the cookie in the browser, causing repeated unauthenticated requests to resend it.
- Decision: expire a present malformed token and any token that does not resolve to a current active session, using the same `__Host-` cookie path/security attributes. For valid-format rejected tokens, revoke any still-live matching session record before clearing the cookie. Preserve cookies on the database-unavailable 503 path.
- Consequences: stale/revoked/expired/inactive sessions are cleared by the normal session check; an inactive account/role cannot regain an old session if reactivated. Temporary database outages do not sign users out locally. Logout uses the same cookie-expiration attributes.
- Validation: API typecheck/build and `git diff --check` passed; no test suite or database access in this slice.
- Rollback: remove cookie expiration from `/auth/me`; keep the shared expiration attributes used by logout. No DB rollback is needed.

## ADR-033 — Preserve sessions during authentication-store outages (2026-11-26)

- Status: implemented locally.
- Context: `/auth/me` documentation promises 503 with the existing browser cookie preserved when PostgreSQL is unavailable, but a thrown lookup/revocation error was passed to the global error handler and became 500.
- Evidence: the regression test first reproduced HTTP 500 using a synthetic unavailable DB. After the change, the test observed HTTP 503 and no session-cookie expiry; a separate synthetic query failure with a successful connectivity probe still returns 500.
- Decision: on a failed session lookup or stale-session revocation, probe PostgreSQL once. If the probe also fails, log only a fixed event and request ID, return 503 `authentication_unavailable`, and do not mutate the cookie. If PostgreSQL responds, rethrow the original error so application/query faults retain generic 500 handling.
- Consequences: transient store failure no longer appears as a valid anonymous session and does not clear client state. The extra DB probe occurs only on an exceptional auth lookup/revocation path.
- Validation: auth integration test passed with 38 expectations on local PostgreSQL using rollback-only synthetic fixtures; workspace typecheck/build and `git diff --check` passed. No live account or production database was used.
- Rollback: restore direct lookup/revocation behavior in `/auth/me` and remove the regression cases and this ADR; no schema or database rollback is required.

## ADR-034 — Share transaction-aware audit event insertion (2026-11-26)

## ADR-035 — Add scoped ticket list with signed keyset cursors (2026-11-26)

- Status: implemented locally; `tickets.read` remains an unseeded candidate pending owner approval.
- Context: Ticket Management had exact incident detail but no bounded list/search path. Lists, direct filters, and detail must enforce the same permission and hierarchical scope, and deep offset pagination is excluded by query standards.
- Decision: add `GET /tickets` with a 50-row default and 100-row maximum, exact incident/service-number search, exact stored status and operational bucket filters, canonical lifecycle filters, and optional hierarchy ID filters that only intersect access. Use the shared `ticketAccessPredicate` in the same Drizzle query; return an explicit projection without service number, summary, or detail. Do not add total-count queries.
- Cursor contract: order by `reported_at DESC NULLS LAST, id DESC`; preserve PostgreSQL microseconds as UTC text to avoid Date millisecond truncation. HMAC-sign cursor claims bound to user, permission set, global-scope bit, scope version, and normalized filters. Keep the signing key random and process-local; restarts invalidate cursors. Multi-replica deployments need a shared protected key before they can share cursors.
- Consequences: list and detail share the existing fail-closed authorization predicate and candidate permission. Missing scope yields no rows; missing permission still returns 403. Null reported dates remain pageable at the end. No index, migration, dependency, role grant, KPI rule, or database schema was added.
- Validation: API auth/ticket PostgreSQL integration test passed with 66 expectations and rollback-only synthetic records, including unauthenticated 401 and no-permission 403/private-no-store list/detail denials; cursor unit tests passed (2 tests, 10 expectations); shared authorization integration test passed (1 test, 9 expectations); workspace typecheck/build and `git diff --check` passed. No large-dataset query plan or performance benchmark was run.
- Rollback: remove the list route and cursor codec/tests, revert `listTickets`/exports, and restore the Phase 2/Decision Log/Handover text. No migration or persistent fixture rollback is required.
