## ADR-007 details — 2026-11-26

- Context: scaffold had only `regions → branches → workzones`, direct `user_workzones`, and hardcoded role strings; required model is five levels, multiple scopes and role/action separation. The registered local project database contained no business rows before migration.
- Evidence: schema migration generated by Drizzle and applied with the Bun SQL Drizzle migrator; local PostgreSQL 18.7 reports 19 public tables, 21 FKs, a `NULLS NOT DISTINCT` scope unique index, and the exactly-one-target check. Synthetic insert/rejection checks passed inside a rolled-back transaction.
- Decision: represent `area → region → branch → service_area → workzone`; scope grant targets exactly one typed FK; use a role-permission catalog rather than legacy role enum. Leave roles, permissions, master data, users and grants unseeded until policy/crosswalk decisions are approved. No Workzone aliases are introduced without evidence.
- Consequences: current scope handles overlap at the data model and prevents duplicate identical grants; application resolver and deny-by-default API enforcement are still required. Total table count is now 19, not 17, because of separate new hierarchy and RBAC entities. Existing scaffold-only columns/tables are removed by migration `0001`; the migration is unsafe for a database containing data and must not be promoted as-is.
- Rollback: no down migration is generated. On the empty local database, a reset requires verified target identity and a reviewed reverse/recreate procedure. For any nonempty database, create a reviewed additive data-preserving migration and backup first.
- Validation: `bun run typecheck`, `bun run build`, `bun run db:generate`, `bun run db:migrate` (including repeat run), PG catalog checks, and synthetic transactional scope-constraint assertions passed. No owner approval of role mapping, crosswalk, or production rollout is implied.

## ADR-008 details — 2026-11-26

- Context: schema and shared authorization lookup existed, but API had only health routes. Security.md requires opaque hashed sessions, Argon2id, strict Origin and CSRF checks, generic login failures, throttling, and active identity revalidation.
- Evidence: Elysia 1.4.32 and Bun 1.4.5 are pinned in the project; Context7 docs were checked for Elysia cookie/app.handle behavior and Bun 1.4.2 password APIs. Synthetic integration tests against local PostgreSQL exercised CSRF/Origin rejection, Argon2id login, cookie flags, session read/revocation, generic invalid credentials, and throttling.
- Decision: add `/auth/csrf`, `/auth/login`, `/auth/logout`, `/auth/me`; store only SHA-256 of random 32-byte session tokens; keep credential/session SQL in the DB package. CSRF uses a random cookie/header double-submit pair with constant-time comparison and exact configured Origin validation. Use bounded process-memory account/IP counters with a conservative 10 failures per 15 minutes while deployment remains one API process; do not trust forwarded IP headers.
- Consequences: no new dependency or schema object. Login requires a configured `APP_ORIGIN`. Permission resolution is current per `/auth/me`, but protected product routes and administrative mutations still need shared guards. The limiter resets on restart and cannot coordinate replicas; scaling out is blocked until a durable shared approach is reviewed.
- Rollback: revert `apps/api/src/auth.ts`, `apps/api/src/app.ts`, `apps/api/src/index.ts`, `packages/db/src/authentication.ts`, exports and tests, plus this ADR and Phase 2/Handover notes. No migration or persistent business data change; tests roll back their transaction.
- Validation: `bun run typecheck`, `bun run build`, `git diff --check`, and `bun --env-file=.env test apps/api/src/auth.test.ts` passed; the auth test reported 1 pass and 28 expectations. `packages/db/src/authorization.test.ts` also passed (1 test, 9 expectations). Database user/role/session counts remained 0 after rollback. Production deployment and horizontal scaling are not approved by this decision.
- Follow-up: `createPermissionGuard` adds Elysia's `requirePermission` macro; a protected route receives the fresh authorization context only after session+permission checks. It sets `Cache-Control: private, no-store`. Integration coverage includes missing-session 401, authorized 200, missing-permission 403, and no-store. This remains a reusable extension; no business route exists or is protected yet.

Append ID/date/status/context/evidence/alternatives/decision/consequences/test/rollback/owner approval if required. Supersede rather than erase decisions. Update schema, docs and Handover in same change.

## ADR-009 — Configurable local API proxy (2026-11-26)

- Status: implemented locally; development-only.
- Context: local login uses same-origin Vite proxies for `/auth`, `/tickets`, and `/health`. API port 3000 was occupied by an unrelated/unidentifiable listener during local verification.
- Evidence: API and web started on loopback ports 39871 and 5173; proxied `GET /auth/csrf` returned 200 and proxied `GET /auth/me` returned the expected 401 for anonymous access. No login credentials or DB writes were used.
- Alternatives: stop the listener on 3000 (not safe because its owner was not identified); keep a fixed proxy and leave local login unavailable while the port is occupied.
- Decision: derive Vite proxy target from `process.env.API_PORT`, with 3000 as the default; both local processes receive the same override.
- Consequences: local development can avoid the port conflict without changing browser origin, CSRF validation, cookies, or production deployment. No dependency or runtime API changes.
- Validation: `bun run typecheck:web`, `bun run build:web`, desktop Chrome render, proxied CSRF/session smoke checks, and `git diff --check` passed. Interactive login/logout with a provisioned synthetic user remains unverified.
- Rollback: restore the fixed `http://127.0.0.1:3000` proxy target and remove the local setup note. No database rollback.

## ADR-010 — Baseline API response security headers (2026-11-26)

- Status: implemented locally.
- Context: Security.md requires `nosniff` and a restrictive referrer policy; the JSON API had no shared hook applying headers to every route, including health and not-found responses.
- Evidence: Elysia 1.4.32 is installed. Its local type declarations and lifecycle reference confirm `onRequest` runs before routing and exposes `set`; API typecheck passed after adding the hook.
- Alternatives: duplicate headers in each route (easy to miss) or configure at deployment proxy only (not all local execution paths use that proxy).
- Decision: set `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer` in a global `onRequest` hook before route registration.
- Consequences: all API responses receive these baseline headers without changing payloads, auth decisions, cookies, or schemas. CSP and HSTS remain deployment-layer controls; do not enable HSTS until TLS is validated.
- Validation: `bun run typecheck:api` and `git diff --check` passed. No HTTP response assertion was run in this slice.
- Follow-up validation: local API on `127.0.0.1:39871` returned the three headers on both `GET /health/live` (200) and an unknown route (404); process stopped after the check.
- Rollback: remove the global hook and this ADR entry; no DB or persistent state changes.

## ADR-011 — Generic API error responses (2026-11-26)

- Status: implemented locally.
- Context: Security.md requires generic errors with request IDs and prohibits query/stack disclosure. Elysia's default development error response can include implementation detail, and validation/not-found errors did not have a consistent correlation ID.
- Evidence: Context7 documentation for Elysia `onError` says returning a value replaces the default response and context supplies error code, error and status. Current API route errors are returned as typed values; thrown/validation/framework errors flow through the app hook.
- Alternatives: rely on production-mode Elysia redaction (does not provide a consistent request ID and is environment-dependent); add handlers per route (easy to miss).
- Decision: global error hook preserves valid 4xx/5xx status, returns only `not_found`, `invalid_request`, or `internal_error` plus a random UUID request ID, and sets `X-Request-ID`. It logs only 5xx event, request ID, framework error code and error type; it never logs message/stack/body/query.
- Consequences: thrown errors, parsing/validation failures and unknown routes no longer reveal framework details through their response. Explicit business errors returned by route handlers keep their existing documented shape.
- Validation: `bun run typecheck:api` and `bun run build:api` passed. Local API smoke checks on `127.0.0.1:39871` verified unknown route HTTP 404 returns only `not_found` and request ID, while invalid login body HTTP 422 returns only `invalid_request` and request ID. The process was stopped after the checks. No synthetic thrown-500 request was run.
- Rollback: remove the global error hook and this ADR entry; no database change.

## ADR-012 — Request correlation on every API response (2026-11-26)

- Status: implemented locally.
- Context: request ID existed only on errors handled by `onError`; handled readiness failures and successful requests lacked a response ID to correlate with operational records.
- Evidence: global Elysia `onRequest` runs before route handlers and can assign response headers. The API's readiness failure handler logs a sanitized event and can reuse the same header value.
- Alternatives: generate separate IDs in each endpoint (inconsistent); rely on proxy-generated IDs (not guaranteed in local execution).
- Decision: generate a UUID in the global request hook, add `X-Request-ID` to every API response, reuse it in generic error body and sanitized readiness-failure log.
- Consequences: API consumers can reference a stable per-request ID on successful and handled-error responses; no response payload, auth, business query, or DB schema change.
- Validation: `bun run typecheck:api`, `bun run build:api`, and loopback checks of a success route, 404, and invalid request confirmed an ID header on each; error body IDs match the header. No database request was made.
- Rollback: remove request ID generation/reuse from app hooks and this ADR entry; no persistent state changes.

## ADR-013 — Accurate login throttle retry interval (2026-11-26)

- Status: implemented locally; production deployment remains subject to ADR-008's single-process limitation.
- Context: the login limiter blocked a request when an account or IP bucket reached its threshold, but always returned `Retry-After: 900`, even when the affected bucket would reset sooner.
- Evidence: static review of `LoginLimiter` showed each bucket already records its reset timestamp; the response discarded that timestamp and used the full configured window.
- Decision: calculate the maximum remaining reset interval among blocked account/IP buckets. If the bounded in-memory bucket map is full and a new key cannot be admitted, also account for the earliest bucket expiration that frees capacity. Return a minimum of one second and expose no bucket keys or counters.
- Consequences: rate limit policy and thresholds remain unchanged; clients receive a retry interval consistent with the limiter state. No dependency, database, schema, response body, or logging changes.
- Validation: `bun run typecheck:api`, `bun run build:api`, and `git diff --check` passed. No automated test or runtime DB interaction was performed in this change.
- Rollback: restore the fixed 900-second header calculation and boolean limiter check; no database or persistent state rollback is needed.

## ADR-014 — CSRF token encoding validation (2026-11-26)

- Status: implemented locally.
- Context: the double-submit CSRF check verified JavaScript string length before calling `timingSafeEqual`. Equal character counts can encode to buffers with different byte lengths; Node throws on a length mismatch instead of returning a comparison result.
- Evidence: the generated token is 32 random bytes encoded as unpadded base64url, exactly 43 ASCII characters from `[A-Za-z0-9_-]`; the previous guard accepted other same-character-length strings.
- Decision: require both cookie and header to match the generated token alphabet and exact 43-character form before constant-time comparison. Malformed encodings fail closed as CSRF rejection.
- Consequences: valid generated tokens retain identical behavior; malformed input no longer reaches a throwing comparison. No schema, dependency, response body, or business policy change.
- Validation: `bun run typecheck:api`, `bun run build:api`, and `git diff --check` passed. No runtime request or automated test was performed in this slice.
- Rollback: restore the previous length-only guard; no database or persistent state rollback is needed.
