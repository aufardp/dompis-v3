# Engineering principles
Mandatory: agreed stack, UUID, five-level hierarchy, scoped RBAC, historical migration, NOSSA-only ongoing ticket facts, four menus, no technician assignment, greenfield and append-only Handover. Recommended: modular monolith, single sync worker, static SvelteKit, typed canonical ticket, minimal indexes, direct workzone lookup, SSE. Discovery required: actual field semantics, code uniqueness, KPI, closure date, user scope mapping, data volume, runtime versions. Do not copy legacy implementation. Optimize correctness first, then measured latency and resource use. Prefer simple typed functions, shared domain predicates, SQL aggregation, explicit boundaries, short transactions. Add dependency/table/cache only with evidence and ADR. Changes to technical candidates allowed with tests and docs; business semantics/security/retention changes require owner approval.

## Identifier naming clarity

Name every new or materially changed variable, function, class, type, and constant so a reader can tell what it represents or what action it performs without decoding an abbreviation. Avoid shortened identifiers such as `usr`, `cfg`, `ctx`, `req`, `res`, `tmp`, `val`, `fn`, and single-letter loop variables. Prefer domain-specific names such as `affectedUserIds`, `destinationAreaId`, `loadActiveUserScopes`, and `OrganizationMovePreview`. Boolean identifiers should express a condition (`isActive`, `hasGlobalScope`, `canManageUsers`); functions should use an action verb and identify their subject or effect. Keep names as short as clarity allows, but never at the cost of purpose.

Established domain and technology terms (`UUID`, `SQL`, `HTTP`, `API`, `SLA`, `TTR`, `NOSSA`) are not considered unclear abbreviations. Do not rename third-party API symbols or persisted database/upstream contract fields solely to satisfy source-code naming style. Apply this rule to new code and code materially touched by a scoped change; avoid broad mechanical renames that obscure functional changes.
